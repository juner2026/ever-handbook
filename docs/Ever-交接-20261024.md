## 二、动态配图 —— 已查明，原来这里的判断是错的

> ⚠️ **2026-10-24 08:00 更新：这一节原来的「WebView 被系统回收重载」推断是错的。**
> 真因是**一个拼写错误**，已在 5.71 修掉并验证，见下面「二·更正」。

原推断（**已证伪，别再按它做**）：因为诊断行一直是 0/0/0，推断打开相册时
WebView 被回收、页面重载。但 0/0/0 有更简单的解释：诊断行写在
`momRenderDraftGrid()` 末尾，而那个函数在更早的一行就抛异常了，所以它永远
停在"上一次成功渲染"的旧值上。

### 二·更正：真因是 `meta is not defined`

`TidalEcho-手帐桌面.html` 里 `momRenderDraftGrid()` 的调试分支：

```js
var m=_momDraftMeta[k]||{};          // 作用域里只有 m
if(window._momDbg){
  var _sk=(meta.srcKind||'?'), ...   // ← 写成了 meta
}
```

而 `window._momDbg` 在 5.68 被写死成 `true`。于是**只要草稿里有一张图**，
`momRenderDraftGrid()` 第一行就抛 `ReferenceError`：
格子一个都画不出来、诊断行也执行不到 → 用户看到「选了图，格子不出现」+
计数永远 0/0/0。**跟相册、跟 WebView 回收都没关系。**

5.71 的修法：
1. `meta` → `m`（根治）
2. `window._momDbg` 默认 `false`，长按「＋」才开
3. 诊断行只在调试开着时显示，平时不占面板
4. 「＋」保持 `label[for]`→input→change 那条**已验证可用**的路；
   原生选图降级为**兜底**：相册 12 秒没交回图时才叫它

验证证据（Chromium 端到端，**非真机**）：点「＋」→ 选择器交回 9 张 → 9 格
全部 `naturalWidth>0` → 发表 → 动态流里 9 张全在。截图见
`修复验证截图/5.71-动态配图/动态九宫格-发布后.png`，脚本 `/root/momtest/mom71.mjs`。

### 二·原生选图桥（5.70 加的，5.71 起降级为兜底，代码保留）

`MainActivity` 里已实现 `EverNative.pickImages()`：ACTION_GET_CONTENT 多选 →

### 二·明信片「寄了但看不见」（5.72，源码已改，待打包）

实测发现跟"图丢了"没关系 —— 图和记录都好好存着。真正的三处：

1. **地图区空白**（主因）：`renderPostcard()` 用的 `shapes` 只有地图页
   `loadMap()` 跑过才有值。没进过地图页就寄卡片 → 左边一块纯浅蓝，
   等于一张空卡片。修法：`renderPostcard` 一进来就用 `decodeTopo(BUILTIN_MAP)`
   把 `shapes` 补上（**只填数据，不动 `inited`/画布**，地图页照旧自己初始化）；
   连内置数据都没有时画经纬网兜底。
2. **目的地没标出来**：`findCountry()` 原来在补数据**之前**调用，cold start
   时永远返回 null → 卡片不居中、没有红点。修法：把补数据提到 `findCountry` 前面。
3. **重进聊天页后卡片变样**：`tepc_` 图被当普通图气泡画，紧跟的
   `_toolCard:postcard` 又画一张「1 次工具调用」→ 同一张卡像两条，图还被压成
   小方块。修法：历史渲染里加 `tepc_` 分支，还原成 `.te-postcard-card`
   并置 `_travDrawn=true` 抑制重复工具条；顺手给历史条目补 `ts`（时间才准）。

验证（Chromium）：地图区非底色像素占比 0% → **29%**；目的地居中 + 红点；
重进/刷新后仍是 1 张明信片卡片、0 条重复工具调用。
截图 `修复验证截图/5.72-明信片/`，脚本 `/root/momtest/postcard72.mjs`。

**还没做的**：AI 那条硬闸（`window._teAskedCard`）在用户没提"明信片"时会**静默丢弃**
卡片，但 AI 正文已经写了"我寄给你了"—— 用户会真的"寄了但看不见"。
这是设计取舍（5.66 为了治"莫名收到明信片"加的闸），没动。真要治，
应该在被拦时补一句旁白（照 `_teTravelDenied` 的做法），而不是放开闸。

### 二·侧边「多了很多很多个窗口」（5.74，已修，Chromium 验过）

真因：`convSaveAll()` 的语义是**只存当前 AI 的窗口**——
`mine = 传进来的`，`others = 磁盘上别人的`，最后 `others.concat(mine).slice(-500)`。
但有 **7 处调用方**（自主唤醒投递 / AI 绑定 / 解绑 / 清聊天记录 / 导入…）
图省事直接传了 `convAll()` **全量**列表。于是"别人的窗口"既在 `others` 里、
又在 `mine` 里，**每调一次就复制一份**。

实测（旧逻辑，从 5 条开始，每次传全量）：

| 调用次数 | 0 | 1 | 2 | 3 | 4 | 5 | 25 |
|---|---|---|---|---|---|---|---|
| 窗口条数 | 5 | 8 | 14 | 26 | 50 | 98 | **500（封顶）** |

所以侧边栏会一路翻倍堆到 500 条 —— 这就是「莫名其妙多了很多很多个窗口」。

修法（`convSaveAll` 内部，一处根治全部调用方）：
1. 传进来的列表按 `id` 去重；
2. `others` 里排除掉已经在 `mine` 里的 id；
3. 合并后整体再按 id 去重，保留最后出现的那份（`mine` 比 `others` 新）。

另外加了 `convDedupe()`（启动时跑一次）：把历史里**已经被复制出来的**重复窗口清掉。
只按 `id` 判重（同一条对话存了多份），不是按标题 —— 不会误删真的两个窗口；
保留消息更多 / 更新的那份。测试：5 条正常数据 5 次全量保存仍 5 条；7 条脏数据清成 5 条。
脚本 `/root/momtest/conv74.mjs`、`old74.mjs`。

**注意**：这个 bug 的触发点在「自主唤醒投递给**非当前** AI」那条路（`_all2` 那段），
以及 AI 绑定 / 解绑。也就是说它跟你平时切 AI、开自主心跳的次数正相关。

### 二·明信片「寄了但看不见」—— 真因（5.77）

**症状**：用户说「再寄一张明信片」（句子里有"明信片"），AI 回复也像寄了，聊天里却什么都没有。

**真因：`_teAskedCard` 在派发之前被清掉了。** `callChatAPI` 里按她那句话算出
`window._teAskedCard`；但回复处理流程的顺序是：

```
① 「兜底」段（模型没调用时补一张）…… 末尾无条件执行 window._teAskedCard = false;
② 出行 [[travel:]] 段
③ 真正的工具派发：else if(tc.type==='postcard'){ if(!window._teAskedCard) return; }
```

于是**只要 AI 真的调用了明信片**（`_pcSent=true`，兜底段什么都不做），标志也会
被 ① 清成 false，③ 就把它当成"她没提明信片"**静默丢掉**。
所以：模型越听话、越真的去调，卡片反而越一定被丢 —— 前端怎么改都没用。

**5.77 修法**：
1. 删掉 ① 末尾那句清零；
2. `_teAskedCard` 改成在 `callChatAPI` 里**无条件重算**（`_lu` 为空也赋 false），
   整条回复期间保持不变，下一轮发请求再刷新。

**怎么确认的**：5.76 给闸加了一句旁白（"TA 想寄一张明信片，但你这句话里没提…"），
用户截图里这句**出现在她自己说了"再寄一张明信片"之后** —— 自证。

另外：5.76 加的「测试：直接寄一张明信片（不走 AI）」按钮已证明
**生成 / 上屏 / 入库 都是好的**（自测卡片正常出现），所以问题只在闸。

## 九、5.90（「取消不了」的真凶终于抓到了：面板根本没关过）
